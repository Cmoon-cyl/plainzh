## 几组短例子

PlainZH 是一套中文写作 Skill，帮助 Agent 理清信息、改顺句子，也照顾读者和写作场合。清楚的句子可以保留，必要的标题、解释和礼貌也有各自的作用。

| 想改好什么 | 原文 | PlainZH 改写 |
|---|---|---|
| 直接说动作 | 为了保障维护工作的顺利开展，系统操作人员应于维护开始前完成数据备份操作。 | 系统操作人员请在维护开始前备份数据。 |
| 保留完成状态 | 我们已经完成了对方案的讨论，结论是暂不发布。 | 方案已经讨论完，结论是暂不发布。 |
| 把话说顺，保留判断的把握 | 关于你提到的报错，我初步看了一下，可能与配置有关，后续会进一步排查，有结果再告诉你。 | 我初步看了这个报错，可能与配置有关。我会继续排查，有结果再告诉你。 |

第一例没有给出维护时间和备份范围，改写不会擅自补齐。第二例仍然是“讨论完了”。第三例仍然是“可能”，也没有额外承诺回复时间。

**有些句子，原样保留就很好。**“两名操作人员必须同时按下按钮 A 和按钮 B。”已经清楚，改成先后两步反而会改变要求。[更多短例子](references/examples.md)。

## 方法从哪里来

### ISO 24495-1：从读者要完成的事出发

PlainZH 采用 ISO 24495-1:2023 的四项清晰语言原则，决定该写什么、怎么组织，以及怎样检查结果。下面是本技能对这些原则的中文实践。

| 原则 | 对 Agent 的具体要求 |
|---|---|
| 内容切合需要 | 先判断读者是谁、要做什么；保留影响判断的条件、例外和证据。 |
| 容易找到 | 把关键结论或行动放在合适的位置；用小标题组织主题，用编号呈现步骤。 |
| 容易理解 | 写清谁对什么做什么，理清指代和条件；按读者需要解释术语。 |
| 能够使用 | 操作说明要能照着做，方案要交代依据和限制，解释要回答读者的问题。 |

它也影响验证方式：模型回读只能算文本自查。需要检验实际效果时，应让代表性读者查找信息、复述含义或尝试操作，观察哪里会卡住。

### ASD-STE100：让技术表达更明确

ASD-STE100 面向英语技术文档。PlainZH 参考 Issue 9 的写作方法，把适用于中文的部分用于操作指南、接口说明和故障处置：

- **名称一致**：同一对象沿用同一名称，保留命令、参数和状态值，避免为了换词而引起误认。
- **条件先行**：先说明何时可以操作，再写动作；分清先后、同时执行和需要等待的关系。
- **要求清楚**：独立操作按步骤写，必须执行的动作放在正文中；备注用于补充解释。

中文不套用英文受控词表、词性限制或英文单词数上限。这是独立的中文实践技能，不是标准译本或认证工具。[标准来源与适用边界](references/sources.md)。

## Agent 怎样改稿

[SKILL.md](SKILL.md) 将这些方法落到一次改稿的过程里：

1. **通读并理解场合。**判断读者、目的、原文各段的作用，以及允许修改的范围。“只润色”与“重写”采用不同的处理方式。
2. **识别必须保留的信息。**保护数字、日期、术语、引用和链接，以及因果、否定、条件、概率和承诺。
3. **解决具体的阅读问题。**调整信息顺序，理清指代，减少套话和重复；保留有用的标题、解释和已经清楚的句子。
4. **照顾语气与沟通目的。**汇报先呈现工作进展，限制在相关正文中说明；专业文本保持专业，通知保留必要的礼貌，不擅自增加批评或夸大成果。
5. **双向核对后交付。**从原文检查有没有遗漏，从改稿检查有没有新增事实。歧义无法消除时指出缺项，不替作者猜答案。

这些检查通常在改稿过程中完成。默认交付正文；需要修改说明或前后对照时，可以直接提出。

<details>
<summary><strong>故障排查：为什么备用压缩成功，任务仍反复压缩</strong></summary>

**改写前**

> 反复循环的主放大器是备用压缩的状态处理语义不一致。常规压缩成功会清历史消息、用摘要替换新增消息；备用压缩却只压缩新增消息，历史消息和固定上下文都保留。与此同时，旧版分段逻辑不是 token-aware、merge 后没有二次归并，也没有压缩后目标水位和冷却区间。结果是备用压缩在技术上成功、在压缩水位上却不合格，任务很快再次触发。

**PlainZH 改写**

> 备用压缩与常规压缩处理的内容不同。常规压缩成功后，会清空历史消息，并用摘要替换新增消息；备用压缩只处理新增消息，保留历史消息和固定上下文。
>
> 备用压缩还有几个限制：分段时不按 token 数控制大小，合并结果后不再做一次归并压缩，也没有设定压缩后的目标长度和两次压缩之间的冷却间隔。
>
> 因此，备用压缩返回成功时，整个请求仍可能过长。任务继续执行后，很快就会再次触发压缩，形成反复循环。

把“状态处理语义不一致”展开为两条流程的具体差别，再解释反复压缩的原因。[查看完整案例](showcase/incident-analysis.md)。

</details>

<details>
<summary><strong>技术方案：把一段密集规则拆成可查找的条件</strong></summary>

**改写前**

> 状态库记录写前意图、请求hash、远端引用、事件游标、attempt、锁/租约及outbox。相同operation_key只代表同一请求；同key不同hash冲突。submit结果unknown时先reconcile原写入；后端不能核对则停留unknown，不能为了继续验收重提。等待超时只停止本地等待，不默认取消远端任务。取消按资源所有权和精确运行引用进行，不能取消同Session其他调用。

**PlainZH 改写**

> **保存恢复所需的信息**
>
> 状态库需要记录准备执行的写入、请求 hash、远端引用和事件游标，还要保存 attempt、锁或租约，以及 outbox。这些信息用于判断上次执行到了哪里，以及请求是否可以继续处理。
>
> **分清重试、超时和取消**
>
> - **请求去重**：同一个 `operation_key` 对应同一请求。如果 key 相同但 hash 不同，报冲突。
> - **提交结果未知**：如果 `submit` 返回 `unknown`，先用 `reconcile` 核对原来的写入。后端无法核对时，保留 `unknown`，不能为了继续验收而重新提交。
> - **等待超时**：只停止本地等待，默认不取消远端任务。
> - **取消任务**：根据资源归属和精确的运行引用执行取消，不能影响同一 Session 中的其他调用。

规则都保留，篇幅略有增加，但开发者可以按场景找到对应的处理方式。[查看完整案例](showcase/technical-proposal.md)。

</details>

## 安装

通过 [Skills CLI](https://github.com/vercel-labs/skills) 安装到支持的 Agent：

```sh
npx skills add Cmoon-cyl/plainzh
```

## 使用

直接提供文字、文件或起草材料，例如：

```text
用 $plainzh 改写这段产品介绍，让第一次接触产品的人看懂。

[粘贴原文]
```

也可以指定场合和范围：

- `用 $plainzh 修改 docs/onboarding.md，读者是第一次接入的开发者。`
- `用 $plainzh 润色这份报告，保持章节结构。`
- `用 $plainzh 根据下面的时间、影响范围和准备事项，起草维护通知。`

默认给出正文。需要的信息不全时，会指出缺项；已经清楚的句子可以保持原样。
