# 故障排查：为什么备用压缩后还会再次触发

[全部案例](README.md) / [PlainZH](../README.md)

场景：常规的上下文压缩失败后，系统会启用备用压缩。排查发现，备用流程返回成功后，任务仍反复触发压缩。下面是对这一机制的分析。

## 改写前

反复循环的主放大器是备用压缩的状态处理语义不一致。常规压缩成功会清历史消息、用摘要替换新增消息；备用压缩却只压缩新增消息，历史消息和固定上下文都保留。与此同时，旧版分段逻辑不是 token-aware、merge 后没有二次归并，也没有压缩后目标水位和冷却区间。结果是备用压缩在技术上成功、在压缩水位上却不合格，任务很快再次触发。

## 改写后

备用压缩与常规压缩处理的内容不同。常规压缩成功后，会清空历史消息，并用摘要替换新增消息；备用压缩只处理新增消息，保留历史消息和固定上下文。

备用压缩还有几个限制：分段时不按 token 数控制大小，合并结果后不再做一次归并压缩，也没有设定压缩后的目标长度和两次压缩之间的冷却间隔。

因此，备用压缩返回成功时，整个请求仍可能过长。任务继续执行后，很快就会再次触发压缩，形成反复循环。

## 为什么这样改

“主放大器”“状态处理语义不一致”概括了问题，却没有直接告诉读者哪个流程保留了哪些内容。改写先比较两条流程，再说明分段、归并和触发限制，最后解释为什么会反复压缩。

“技术上成功、压缩水位不合格”改成“返回成功时，整个请求仍可能过长”。它说明了成功回执与压缩结果之间的区别，也保留了这一段讨论的故障机制。

## 核对原意

- 常规压缩清空历史消息，并用摘要替换新增消息；备用压缩只压缩新增消息，保留历史消息和固定上下文。
- 旧版分段不按 token 数控制大小，合并后没有二次归并。
- 没有设定压缩后的目标长度和冷却间隔。
- 备用流程返回成功，不保证整个请求已缩短到合适长度，任务可能很快再次触发压缩。
