# 故障分析：为什么压缩后又触发压缩

[全部案例](README.md) / [PlainZH 首页](../README.md)

**写给谁**：需要理解故障机制的开发者。常规上下文压缩失败后，系统启用备用压缩，但备用流程返回成功后仍反复触发压缩。

**材料来源**：沿用本仓库已公开的技术片段；改稿为编辑演示，不是某次测试的原始输出。

## 改写后

备用压缩与常规压缩处理的内容不同，这是反复触发压缩的主要放大因素。常规压缩成功后，会清空历史消息，并用摘要替换新增消息；备用压缩只处理新增消息，保留历史消息和固定上下文。

旧版分段逻辑不按 token 数控制大小，合并结果后也不再做一次归并压缩。此外，没有设定压缩后的目标长度和两次压缩之间的冷却间隔。

因此，在这次故障中，备用压缩虽然返回成功，整个请求却仍然过长。任务很快再次触发压缩，形成反复循环。

反复循环的主放大器是备用压缩的状态处理语义不一致。常规压缩成功会清历史消息、用摘要替换新增消息；备用压缩却只压缩新增消息，历史消息和固定上下文都保留。与此同时，旧版分段逻辑不是 token-aware、merge 后没有二次归并，也没有压缩后目标水位和冷却区间。结果是备用压缩在技术上成功、在压缩水位上却不合格，任务很快再次触发。

## 为什么这样改

先交代两条流程分别处理了哪些内容，再说明分段、归并和触发方面的限制，最后解释为什么反复压缩。这里需要保留推理过程，不能只把结论改短。

“旧版”限定分段逻辑的适用范围，不能省掉。本例已确认请求仍然过长，因此保留这一确定判断，不改成“可能过长”或“无法判断是否过长”。

## 哪些含义必须保留

- 常规压缩成功后清空历史消息，并用摘要替换新增消息；备用压缩保留历史消息和固定上下文。
- 旧版分段不按 token 数控制大小，合并后没有二次归并。
- 没有设定压缩后的目标长度和冷却间隔。
- 本例中备用流程返回成功，但整个请求仍然过长，任务很快再次触发压缩。
- 原稿指出主要放大因素，改稿没有把它说成唯一原因。
