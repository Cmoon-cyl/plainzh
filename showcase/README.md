# 改写案例

这些案例选自两份实际完成改写的技术文档：一份技术方案、一份能力评估报告。公开版本去掉产品与平台名称、内部链接和业务细节；其中的通用术语和约束用于说明改写方法。

前后两侧采用相同的脱敏替换。第三例用虚构表格重建实际发生的结构调整；其余例子是经过脱敏的段落摘录。diff 比较的是公开的脱敏文本，不是完整原文。

这里展示改写选择与语义核对，不构成可读性基准测试或真实读者验证，也不代表案例中的技术方案已经实现。

| 案例 | 主要改动 | 需要守住的含义 |
|---|---|---|
| [把流程与存储说明分开](01-separate-topics.md) | 先解释两个阶段及其约束，再另起一段说明维护哪些表、其他数据存在哪里。 | 执行可以不带评测规则；评测可以不安装被测业务 CLI；同一运行记录可以多次评测；两个阶段分别管理状态和配置。 |
| [把异常条件和处理动作放在一起](02-conditions-and-recovery.md) | 将状态记录与幂等约束放在第一段；第二段按结果未知、超时、取消分别说明处理要求。 | unknown 不变成失败；无法核对时不重新提交；本地超时不默认取消远端任务；取消不能影响同会话的其他调用。 |
| [把重复要求提到表格前](03-shared-requirements.md) | 将共同要求放到表格前，明确它适用于每一项；表内只保留各项独有的证据。 | 路径、SHA-256、生成版本、时间和独立复核仍是每项的要求，不能因删除重复文字而变成可选项。 |
| [说明概率究竟能证明什么](04-probability-and-correctness.md) | 直接说明字段表达的是相对倾向，再指出它不等于自动通过结果的正确率，并紧接验证方法。 | 当前输入与候选集合的限定、独立标注集要求，以及概率不能直接证明正确率的结论均保留。 |
| [分清取得证据与作出判断](05-observation-before-judgment.md) | 先完整说明页面行为需要怎样验证，再用独立段落解释程序、决策模型与工具 Agent 的分工。 | 只读最终回复无法验证页面状态；必须实际操作并观察；决策模型不能代替取证。 |
| [保留诊断与根因之间的边界](06-evidence-and-cause.md) | 合并重复解释，先给结论，再说明可观察证据的范围和确认内部成因所需的条件。 | 诊断方向不是已确认根因；输入与输出的关系不能直接解释模型内部机制；确认成因仍需额外实验。 |

## 如何阅读

先读“改写后”，判断能否找到所需信息；再对照“改写前”和保留的含义，检查条件、否定、状态及责任是否改变。每页附有 unified diff，可核对具体措辞。

这些改法服务于当时的阅读任务。短而清楚的句子无需强行重写；表格若经常按单行摘录，重复要求可能仍应保留。
