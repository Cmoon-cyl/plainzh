# 看看不同文档怎样改

这些样稿由 AI 为演示编写，再按 PlainZH 改写。场景和数据均为虚构，输入完整展示，没有隐藏的补充事实。每页都有改写前后、修改理由和原意核对。

### [产品介绍：直接说明新功能](product-update.md)

开头和结尾都在解释搜索的好处，读者真正要找的功能却埋在中间。改写直接交代能搜什么、怎样筛选、哪些版本可用。

### [项目进展：让完成项和阻塞一眼可见](weekly-update.md)

删除重复介绍“推进工作”的段落，把具体进展放到开头。把下周的计划与它依赖的确认时间放在一起，保留尚未验证的效果和开放范围。

### [故障通知：先说影响、恢复状态和用户动作](incident-notice.md)

把用户最关心的影响、恢复状态和需要采取的动作放在前面，再交代排查进展。只删去态度表述，保留立即处理这一事实和通知中的礼貌。

### [技术方案：先给建议，再说明流程和范围](technical-proposal.md)

把建议写进标题，按处理顺序说明系统行为，把状态含义紧接在流程后面。结尾保留本阶段范围和兼容要求，不再重复“改善体验”。

## 案例的参考来源

选题时阅读了以下项目，参考它们用完整段落展示改写、按阅读场景解释修改的方法。本目录的样稿和改写均为本项目原创，没有翻译或搬用它们的例文。

- [Humanizer](https://github.com/blader/humanizer)：从完整的发布说明展示前后差别。
- [Humanizer-zh](https://github.com/op7418/Humanizer-zh)：用不同场景说明信息、语气和不确定性的保留。
- [The Elements of Style](https://github.com/obra/the-elements-of-style)：清楚、直接的写作原则与按需阅读的参考材料。

这些案例用于展示编辑选择，不是盲评或效果基准。不同模型的实际输出可能不同。
